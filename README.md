# DSE-28
This repository documents the work of group 28 (HUGO) of the Design Synthesis Exercise, bachelor graduation project of BSc Aerospace Engineering at TU Delft, in the academic year 2025/2026. The project is titled 'Micro turbine-powered unmanned flying laboratory designed for testing highly flexible aircraft'.

## Code structure
The code is divided into two completely separate folders: `src_midterm` and `src_final`, containing the code for the Midterm and the Final work packages separately.

### The Midterm work package code
The purpose of the midterm code is to size the four design options to just meet the requirements, so that comparison between them is possible. The sizing of the option is iterative - each option is represented by a single source of truth (SSOT) object (`DesignOptionState`) that gets updated by a set of analyses. The SSOT architecture is implemented to allow for consistent updates, e.g. wing surface is encoded in as a variable, but span as a property. There is thus only one way to update the wing size (by wing area), and chords and spans will be automatically computed. This also helps with including all the consequences of parameter changes for the sensitivity study.

The `Sizing_Loop` folder. The `DesignOptionState` is a composition of `DesignOptionStateIterable` and `DesignOptionStateFixed`. The updating is carried out inside a `DesignOption` class, containing a `DesignOptionState` instance and a list of `DesignOptionStep` objects, specifying the analyses to be executed. The sizing is conducted in `src_midterm/scripts/midterm/main.ipynb`, using the `SizingForTradeoff` class, while the sensitivity studies are conducted in `src_midterm/scripts/midterm/main.ipynb`. **Please note that due to changes to the repository made at the beginning of the Final work package, the midterm code is currently not executable - changing the `src_midterm` folder name to `src` is necessary to run the code.** 

The `objects` folder houses the objects from which `DesignOptionStateIterable` is composed.

The analyses are self-contained allowing for independent testing. For the purpose of the iteration, they are warped by child classes of `DesignOptionStep`. The analyses include:

1. `Drag` - C_D0 estimation using component buildup method. There is a parent `Component` class from which classes representing various components of the aircraft inherit. The drag contributions of each components are combined in the total CD_0 using the `estimate_CD0` function. 
2. `LandingGear` - `landingGearLength.py` contains the optimiser specifying the landing gear placement that specifies main landing gear euclidean distance from the centerline of the aircraft
3. `Class_I` - contains fuel fraction and statistical weight estmation. The fuel fraction estimation models the mission as three `MissionSegment` objects for cruise, mach max. and go-around. For each segment, its individual equivalent range and fuel mass fraction is computed and those results are combined into global fuel mass fraction.
4. `MatchingDiagram` - there is a generic `MatchingDiagram` class that finds an optimal point on a wing loading - thrust-weight ratio graph for general wing loading / thrust weight ratio constraints. `MatchingDiagramJet` inherits from it, providing constraints typical for a jet aircraft, such as climb gradients, maximum speed, approach speed, or landing field length.
5. `Structural_Weight_Penalties` houses the code made while developing and testing the weight penalties method used to estimate the empty mass fraction of the design options. The `fuselage_loading_model_cylinder.py` contains all functions used in the iterative sizing
6. `aerodynamic_model` and `airfoil` the files that contain a wrapper around a modified (inviscid) version of `aerosandbox`'s LiftingLine, used to predict the lift and induced drag characteristics for the Midterm.
7. `flight_envelope` - contains the flight and maneuver envelope of HUGO

### The Final work package code
The Final code executes its analyses for the standard, as well as the 96 critical planforms and asses if the requirements are met for each of them. Hence, the SSOT architecture is dropped in favour of intermediate results (drag and weight estimation) caching using `pickle`. This is because the objects are expected to be *evaluated* not *updated*, but the number of evaluations is high due to the amount of critical planforms. The matching diagram and the fuel fraction part of the Class I analysis are taken directly from the midterm code, while other analyses are reworked:

1. `Drag` - now caches the per-component CD0 results in the components themselves. The objects representing parts of the aircraft, such as `src_final.Aircraft.Planform` and `Fuselage` now inherit from the Component class, hence they save their component C_D0 values and can be included in the drag estimations directly. The drag cache is in form of dictionaries for component C_D0 and drag area contributions with flight condition names as keys.
2. `Aircraft` - the data about the aircraft is separated into `Fixed` object and a list `Planform` objects. The former represents the fuselage group of HUGO, while the latter (in that order), the main wing, horizontal stabilizer and the vertical stabilizer. This replaces the `objects` folder from the midterm code base. The `Planform` class is further expanded to contain estimations of 3D aerodynamic properties from the provided cross section properties.
3. `EmpennageSizing` - contains horizontal stabilzer sizng cross-verified with Flow5, replacing one done in the Mideterm using the `aerosandbox` model. There is a parent class `EmpennageFinder` whose purpose is to add and size a horizontal and a vertical stabiliser for provided `src_final.Aircraft.Planform` and `src_final.Aircraft.Fixed` representing the main wing andd the fuselage group, and child classes for t-tail and canard empennages. This utilizes the formulae from the final report together structurally sizing the empennage (by `src_final.structural_analysis.iterative_planform_sizing.py`) and with iteratively updating the centre of gravity of the entire aircraft.

The requirement checks work as follows. The standard planform, or each of the 96 planforms with their mass and drag pre-computed using `src_final/notebooks/planforms_pickle.ipynb`, is paired with the fuselage group, and an canard/t-tail is sized, creating an `src_final.Aircraft.Aircraft` object. This objects is passed through a list of `Requirement` objects in the `src_final.Requirements` folder, that assess whether a given aircraft complies with the requirement from the Final Report they represent. The list comprises of `MDReq`, `FuelReq`, `LGReq`, `MassReq`, `EmpennageReq`, child classes of `Requirement` verifying respectively whether the aircraft is in the matching diagram feasible design space, if it has sufficient fuel, whether geometric constraints of the landing gear are met, if it is below the MTOM threshold, if its empennage is not oversized. Again, the requirement classes may wrap the anlayses, such as `MDReq` wrapping the `MatchingDiagram`.

Several independent analyses (not invloved in the global requirement check but ran before or afterwards) are added:
1. `landing_gear_tuning` - provides the parameter sweep of the landing gear stiffness and damping, allowing for a tradeoff between shock absorber displacement and the landing force. The maximum force experienced by the structure influences the load factor of global fuselage structural analysis. Needs to be run before structural analyses and thus before the requirement checks.
2. `structural_analysis` - contains the flutter and structural analysis of the standard planform and the fuselage, as well as the `iterative_planform_sizing.py` file used to size a generic planform for constraints other than flutter (there is no guarantee that every point in the Planform Envelope is flutter-free, in fact, due to the objectives of HUGO, it is highly likely and desired for some of the in-envelope planforms to have a flutter speed below Mach 0.75). Needs to be run before the requirement checks.
3. `Noise` - noise estimations for the standard planform, ran after the requirements checks
3. `Emissions` - emissions estimations for the standard planform, ran after the requirements checks
3. `FuelCG` - estimations of the centre of gravity movement achievable through pumping fuel between the aircraft tanks (for the standard planform as well), ran after the requirements checks.
4. `AileronSizing` - in the end not used much since large discrepancies were found between ADSEE and Flow5 predictions and the ailerons were sized by means of analogous estimation and only checked using the developed code and Flow5.
5. `SensitivityStudy` - examining how the standard planform mass is affected by the assumed empennage aspect ratio and computed to total planform mass correction factor. Parallel to the requirement checks.
